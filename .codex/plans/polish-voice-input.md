# Polish voice input in Add Word

## Task and goal

Add a microphone to Add Word so the user can dictate a Polish word, review/edit it, translate it and save through the existing flow. The app teaches Polish to Russian speakers and has no language settings: recognition uses `AppLanguage.polish.speechCode` (`pl-PL`), with no language picker. Base: `1c8e1accfb322ac2076c8fe96fb7f19d88762b2a`; working tree clean at planning start.

Constraints: iOS 17+, Russian UI copy, native Speech/AVFoundation, no external dependencies or schema changes. Preserve vocabulary, folders, SRS, translation behavior and existing UI tests. No E2E, Playwright or XCUITest creation, edits or execution; no commit/push or branch changes.

## Acceptance criteria

- **AC-1:** An accessible microphone control next to source input starts Polish recognition only after a user tap and both microphone and speech permissions. Requesting/recording/stopping states prevent overlapping starts; recording has a clear stop control and Russian status. Save and pronunciation cannot race active recording.
- **AC-2:** Partial results appear as a separate draft/status; they never replace typed source or trigger translation. Explicit Stop finishes audio input and commits one nonempty recognized result (latest partial if the final result does not arrive within a bounded finalization wait); a natural final result commits once. The resulting source remains editable and translates through the existing debounced flow. Cancel/failure/no speech leaves the preexisting source and translation intact.
- **AC-3:** Denied/restricted permissions, unavailable Polish recognition, audio setup errors and recognition failures have understandable Russian feedback; denied permissions explain enabling access in Settings. No offline guarantee: speech recognition may use Apple servers, and the existing translation providers may receive committed text.
- **AC-4:** Backgrounding, interruption, view dismissal and explicit cancellation invalidate the session and stop/remove the audio tap, engine, recognition request/task and pending permission/finalization work. Returning to the foreground never resumes automatically. Old callbacks cannot overwrite a new session, manual edits or a dismissed view; terminal events are processed once.
- **AC-5:** Starting dictation stops current TTS before configuring capture. Cleanup releases recording resources/audio activation; later pronunciation explicitly restores `.playback` with existing `.duckOthers` behavior, including silent-mode playback.
- **AC-6:** Existing Russian/Polish typing, editable translation, save, category and folder selection remain functional. Committed XCTest tests verify permission/outcome/cancellation lifecycle with a fake backend; tests do not request real microphone access.

## Risks and unresolved decisions

- Recognition availability, accuracy, network use and permissions require physical-device verification; simulator tests cannot establish these. Apple may process speech remotely; existing translators receive committed text.
- Explicit Stop needs bounded finalization so unavailable final callbacks cannot leave the UI stuck. Default to a short documented timeout (approximately three seconds), commit latest nonempty draft only on user Stop, and cancel on interruption/background. This is an implementation constant, not a new setting.
- Audio session changes affect shared TTS: restoration in every `speak` and resource cleanup on every terminal path are required together.
- Integration clarification: disable translation editing alongside source editing, Save and Pronounce while requesting/listening/finalizing. Cancel on `.background`, never merely `.inactive` because permission prompts make the scene inactive. Use approximately three seconds for the bounded finalization wait. A minimal injected recognition-client protocol is sufficient; avoid a generic state framework.
- Same-source handoff: expose `start(onRecognized:)` with one completion callback per successful session, including when the recognized text equals the current source. In Add Word, if the result equals `sourceText`, explicitly call `scheduleTranslation()`; otherwise assign the result and let the existing source observer schedule it. Do not depend on `onChange` for identical text or schedule twice for changed text. Record whether translation was pending/absent when recording started: cancellation/failure resumes that work when no completed translation exists, while preserving a completed editable translation. Add regression coverage proving identical recognized text restarts a cancelled pending translation exactly once, changed text does not duplicate requests, cancellation/failure resumes a missing translation, and completed translation survives cancellation/failure.
- No material product decisions remain. No new language settings, automatic persistence, transcript history or custom recording UI beyond the source-card control.
